## 2. 仅保留两个研究者门禁

### Gate A：方法与 claim 批阅

Codex 提交一个合并决策包，研究者一次性决定：

1. 第二、三项研究的正式术语；
2. 第一项研究新增贡献的最小组合；
3. 第二项研究采用基础 contract，还是把知识生命周期列为正式上探；
4. 哪些 claim 允许进入开题。

输入必须是推荐方案、备选方案、直接竞争、证据状态、工作量和失败条件。不得向
研究者提出开放式“你想怎么做”。

### Gate B：真实用户与科学校准

Codex 提交任务、角色和 rubric 包；研究者只需：

1. 确认任务是否代表生态学家和绿化管理者的真实问题；
2. 从已有关系网络中协调小型目标用户与遥感专家校准组；
3. 批准目标用户、领域评审和评测审计的责任边界；
4. 批准人工评分、反馈数据使用和可能的人体参与/伦理审查路径。

专家“能否找到”不再作为主要门禁。Gate B 的核心是任务真实性、角色分工、
专家劳动预算、争议裁决和数据合规。

## 3. 不作为高强度门禁的事项

- 证据矩阵中的路径、状态和仓库内事实由 Codex 维护；
- 文献搜索、候选去重、source locator 和竞争矩阵由 Codex 完成；
- schema、validator、trace、grader、运行脚本和分析由 Codex 实现；
- 工程选择只要可逆、不改变科学 claim，可自主推进；
- 研究者只需异步纠正仓库外事实，无需为此专门开会。

## 4. 并行工作流

### Track A：总控与证据

- 完成开题证据矩阵；
- 完成术语决策包；
- 把所有工作映射到 E1/C1/C2/C3/C4；
- 保持“设计已冻结”和“结果已验证”分离。

### Track B：URSA 第一项研究

- 在 URSA 内建立 schema、validator、targeted repair 和 trace；
- 保留现有 notebook 作为 published baseline；
- 先运行小型 P0--P3 pilot，不扩展 UI、Agent 角色或分布式 runtime。

### Track C：Chapter 2

- 按现有 L0--L9 loop 完成直接竞争和 claim contraction；
- 将 claim ledger 解释为候选知识治理面，不批量转换为人工 runtime 规则；
- 只对一个任务相关的 10--20 条候选切片补齐证据原文和适用边界；
- 准备 human-reference、model-proposed 与 governed-proposal 的小型构建来源对照；
- 准备最小 contract fixture；
- 人类 Gate A 前不扩展正式实验和知识生命周期。

### Track D：Chapter 3

- 保留北京制图冻结结果；
- 将任务环境、弱样本方法、样本、结果制品、故障和过程日志分层登记；
- 历史日志只标记为 episode reservoir，未结构化前不得写成 RL trajectory dataset；
- 设计目标用户任务、TEVV 指标、故障注入和跨方法比较；
- Gate B 前只做不会依赖真实用户判断的 deterministic MVP。

### Track E：Scientific Research Harness

- 仅做文献矩阵、失效模式和本地 gap analysis；
- 不阻塞 A--D，不要求研究者立即参与。

## 5. WIP 限制

- 每项研究同时最多一个毕业核心 claim；
- 全论文同时最多一个 RL/self-evolution 上探；
- 每次提交给研究者的决策包最多三个实质选项；
- 未通过 human gate 的 candidate 不进入正式中文大纲；
- 下游仓库存在未提交工作时，优先新增文件，避免覆盖活动状态。
- 常态最多并行两个章节执行轨，另加一个只读审计／总控轨；同一仓库同一文件集只允许一个写入者；
- 可以并行做证据定位、静态核对、机械验证和文字准备，但不得并行改变同一 claim、gold、方法版本或正式题目；
- 每个并行任务必须绑定一个 owning repo、一个明确产物和一个停止条件；下游先验证、提交、推送，总控后接收 checkpoint；
- 若两个任务对同一上游决策有依赖，后到任务停在 proposal，不自行解决科学冲突。

## 6. 汇报节奏

### 6.1 三层信息带宽

Codex 持续执行并记录，按以下级别管理研究者输入带宽：

- **P0 立即打断**：不可逆删除／覆盖／force-push，凭据与外部发送，伦理或真实用户数据，付费或高成本运行，24 小时内硬截止，candidate 准备晋级正式 claim／gold／方法冻结，以及同一失败连续出现三次仍无法安全前进；
- **P1 批量汇报**：普通 blocker、范围漂移、证据冲突、重要 checkpoint 完成、跨章依赖变化、需要研究者做的 retain／narrow／reject。进入每日或里程碑决策包，不逐条打断；
- **P2 静默推进**：常规检索、只读审计、测试、可逆工程修改、中间文字、未改变状态的检查。只在摘要中给路径和结果，不要求研究者确认。

以下四类科学情形至少为 P1；涉及正式晋级、伦理、数据权限或不可逆投入时升为 P0：

1. 直接竞争使核心 claim 无法成立；
2. 结果与科学假设方向相反且无法通过一次修复解释；
3. 需要真实用户、数据权限或不可逆资源投入；
4. 准备把 candidate 晋级为开题/论文正式论断。

正常情况下，研究者只接收合并后的 Gate A、Gate B 或节点决策包，不接收逐工具、逐文件、逐实验状态流。

### 6.2 固定汇报合同

每次节点汇报只保留以下五项：

1. `STATUS`：on-track / at-risk / blocked / completed；
2. `DELTA`：自上次以来真正改变了什么；
3. `EVIDENCE`：最多三个可定位的文件、结果或检查；
4. `NEXT_CHECKPOINT`：下一步唯一动作及预计停止点；
5. `NEEDS_USER`：`none`，或仅一个需要研究者决定的问题，并给出推荐默认。

每个汇报最多列三个研究者动作。若没有 P0/P1 事项，不为“保持存在感”生成额外审批。每日自动推进默认只在一次汇总中报告 P1；P0 发生时即时停在安全 checkpoint。

### 6.2.1 研究节点必须先于工件展示（2026-09-04）

研究者指出：能看懂一份图文报告，不等于能看懂它为什么出现、解决了哪个研究问题。这是主管的
解释责任，不要求研究者持续监控工具轨迹。本条补充现有汇报合同，不新增总计划、审批门或自动化。

每次开始一个有界研究步骤，先用自然语言给出“当前核心问题—本轮要消除的不确定性—完成标志—
不会据此证明什么”。结束时先回答该核心问题已解决、部分解决还是未解决，再展示工件。

每份面向研究者的阶段产物，入口至少标明：用途、所属节点、生产者及执行方式、证据级别、未解决项、
下一检查点和是否需要研究者操作。必须区分助手编写的参考脚本、人工／专业参考、第一章系统运行和
正式匹配比较；图表精美或文件齐全不能代替这些身份说明。

默认给研究者一个三十秒可读入口，不让其从若干 README、测试日志和目录结构反推研究进度。节点
写回已有 chapter PLAN 与总控 Resume；细节按需展开，不能再按日期创建一个平行论文总计划。

输出完成、用途成立和方法有效分别报告。常规工程验证由代理完成；仅当研究范围、科学验收、比较
条件或结论接受需要决定时，再合并提出一个具体问题。已接受的方向不重复索要批准。

### 6.3 定时执行的真实性门

只有同时存在可复核的 automation ID、`ACTIVE` 状态、本地执行环境、明确 schedule、canonical
workspace 入口和可查看的运行结果，才报告“已创建”；只有出现 run 状态或结果工件，才报告
“已运行”。仅渲染 `suggested_create` 卡片、只有自然语言计划或只有预定时间，均不得当作已经
执行。repo 内实质进展仍须通过 owning repo 的验证、提交、推送和 checkpoint 门。

### 6.4 验证吞吐与研究者审阅预算

生成工件只有进入匹配的验证通道后才算完成。每个有界工件在开始前声明最低验证级别：

- `V0 deterministic`：schema、路径、引用键、术语、测试、manifest、Git 和数值范围等机械检查；
- `V1 fresh-context review`：由未参与该工件生成的只读 reviewer 检查 claim--evidence、章节衔接、
  不能支持项和范围漂移；同一生成轨迹的自评不能单独充当 V1；
- `V2 researcher gate`：正式 claim／gold／方法／题目、科研异常解释、真实用户与伦理边界，由研究者决定。

执行采用以下限流规则：

1. 新工件开始前先检查 validation debt；若已有两个 P1/V1 工件待复核，或一个 V2 决策临近截止，
   暂停扩展内容，优先关闭验证队列；
2. 定时任务发现任一目标仓库 dirty 时，只有 changed paths 已由 `registry/active_work.json` 中的
   活动锁完整覆盖、且与本轮 file scope 不重叠，才可继续；否则停止写入并报告冲突；
3. 每次写入先登记 owning repo、显式 file scope 与停止条件；提交只能 stage 本轮拥有的明确路径，
   禁止用 `git add -A` 吸收其他任务或研究者的改动；
4. 里程碑 writer 与 reviewer 分离：writer 交付可定位工件和 V0 结果，reviewer 只报告 findings，
   不在同一遍审查中重写文本；
5. 每个节点包只报告 validation debt 的新增／关闭、最多三个证据指针和一个研究者问题。

每周只校准四个运营指标：待验证工件数、单个决策包的实际审阅分钟数、因漏检造成的返工数、
以及升级后证明无需研究者处理的误报数。若审阅队列增长，先减少新生成和提高自动检查覆盖；
若漏检增加，再提高对应高风险工件的 V1/V2 级别，不提高所有任务的汇报频率。

## 7. 父工作区与会话路由

`D:/Projects/phd-thesis` 是科研主管工作区。研究者可以只说 Idea、Ch1、Ch2、Ch3 或具体任务；Codex 按 `workspace_bootstrap.md` 的映射进入 owning repo，不要求研究者手动切换目录。

默认继续使用父工作区的主管会话，适合跨章排序、短时单仓任务、决策包和同步收口。只有满足以下任一条件时，才建议新建用户可见的独立任务：

1. 单仓工作预计跨越多个独立回合，且需要长期直接跟进；
2. 需要独立分支／worktree、独立审批循环或与主管会话不同的上下文边界；
3. 任务可以长期并行且其产物不会改变另一活动任务的 claim、gold 或方法版本。

短时并行优先使用受控子任务：每个子任务只有一个 owning repo 和文件范围，结果回到主管会话统一复核。新建独立任务不等于改变论文 source of truth；恢复仍以仓库中的 `THESIS_STATE.md`、当前执行计划和 chapter brief 为准。
